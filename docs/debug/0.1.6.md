# OpenCDi 0.1.6 — debug notes

Changes between 0.1.5 and 0.1.6. For the debug log itself (location,
`--debug`, message format) see [0.1.1.md](0.1.1.md).

**Requested:** "Is there a save function? If not make sure that the emulator
can save and restore games."

Before 0.1.6, the only thing kept between runs was the NVRAM, where CD-i games
keep their own saves (if they have any). There were no save states.

---

## 1. Save states

**Files:** `opencdi/savestate.py` (new); `opencdi/scc68070.py`, `opencdi/cdic.py`,
`opencdi/slave.py`, `opencdi/mcd212.py` (`STATE_SKIP`, `MCD212.reset_caches()` /
`after_load()`)

A state is taken **between two frames**. `Machine.run_frame()` has returned, and
the video chip is at line 0 with no half-built frame. The state holds:

| part | how |
|---|---|
| CPU | `R` and the 13 run-time globals (`ccr`, `srh`, `usp`, `ssp`, `PC`, `vbr`, `xc`, `ipl`, `nmi_edge`, `stopped`, `halted`, `FRAME_FORMAT`, `TRACE`), read through `cpu.ns`, so states move between the native and the Python core |
| RAM | plane A, plane B, `ram5`, `dvcram` (2.5 MiB); written back **in place**, because the native core points into those pages |
| NVRAM | the 8 KiB and the clock offset |
| devices | every attribute of the SCC68070, CDIC, SLAVE and MCD212 except those in the class's `STATE_SKIP` (references to the machine, statistics, caches) |
| scheduler | `now`, `seq`, the clock, and every pending event as (time, seq, device, method name). Device attributes that hold an event (`timer_event`, `sector_event`, ...) are stored as the event's `seq` and linked to the re-created event on load |
| machine | line, line timeline, frame count, LCD text, the audio resampler's position and last sample |

**Safe file format:** a JSON tree of plain values, plus raw memory blocks
referenced by index, compressed with zlib. Floats are stored as hex, so they
come back exactly. Only two small classes (`DmaChannel`, `Channel`) are
rebuilt, from a fixed list. Nothing is unpickled or executed, so a state file
from somewhere else cannot run code. A value of a type the encoder does not
know stops the save with an error instead of writing an incomplete state.

**Loading** resets the machine first, so anything an older state does not
hold has its reset value. It then fills everything in and empties the MCD212
caches. They are keyed by `state_ver` / `clut_ver`, which a load changes, so
stale entries could otherwise match.

* **Pointer:** the SLAVE reports relative motion. On load, the live pointer
  position is kept and taken as the last position the SLAVE saw, so loading
  does not look like a jump of the pointer.
* **Checks:** the BIOS (CRC) and the disc must be the ones the state was
  saved with.
* **Failures:** before loading, the running state is captured. If the file is
  damaged anywhere in the middle, that state is put back and the game carries
  on.

**Disc id:** a SHA-1 of the track layout and the first 32 sectors of the
first track. A `.chd` and a `.cue`/`.bin` of the same disc give the same id,
and so share their slots. The id is kept on the `Disc` object. The frontend
computes it before the emulation thread starts, so the main thread never
reads the disc files at the same time as the emulation thread (the file
handles are not thread-safe).

**Files:** `~/.opencdi/states/<disc id>/slot1.state` ... `slot9.state`. They are
written to `.tmp` and renamed, so a crash cannot leave half a state.

* A header outside the compressed part (JSON) holds the time, OpenCDi
  version, disc name and id, BIOS CRC and name, region, and a 192x120
  thumbnail. The launcher reads only that part.
* Size: 75-100 KiB.
* Save takes 35 ms and load 17 ms.

**The NVRAM is part of the state:** loading a state also puts back the
games' own saves from that moment. Without that, the game in RAM and the NVRAM
file system could disagree. MAME does the same.

**Debug log:** `INFO state saved to <path> (N KiB)`, `INFO state loaded from
<path> (saved by <version>, <time>)`, and every message shown on screen
(`INFO State saved to slot 2`, `INFO Slot 3 is empty`, refusals with their
reason).

## 2. Hotkeys, launcher, command line

**Files:** `opencdi/frontend.py` (`Emulator.state_action()`, `notify()`,
`draw_osd()`), `opencdi/launcher.py` (`SlotScreen`, `Launcher.choose_slot()`),
`opencdi/__main__.py`

* **F5** save, **F8** load, **F6 / F7** previous / next slot (1-9).
  * The main thread only places the request. The emulation thread carries
    it out before its next frame, which works while paused too.
  * After a save or load the frame pacing restarts, so a slow save does not
    cause a burst of frames. After a load the old position's sound is
    dropped.
* **On-screen message:** drawn at the top left of the picture for 2.5 s, and
  printed. The "unchanged picture is not sent" check (0.1.3) redraws when a
  message appears or goes away.
* **Launcher:** **Save state** (while a game runs) and **Load state** (whenever
  a working BIOS is selected) open a slot screen. It shows each slot's date
  and the highlighted slot's picture, disc, BIOS, region and version.
  * Choosing a slot works with Enter / A, 1-9, or a click or tap on the
    highlighted slot. A first click or tap only highlights it, so a state is
    not overwritten by a stray click.
  * When saving, the screen starts on the first empty slot. When loading, it
    starts on the newest state.
  * **Load state** before a game is started boots the selected BIOS and disc,
    then loads the state. If the state is refused, nothing is left running
    and the launcher shows why.
  * This is how states are saved and loaded on Android, which has no F keys
    (the **MENU** button opens the launcher).
* The launcher menu now has up to nine items, which are spaced closer
  together.
* `--headless N --load-state FILE --save-state FILE`: for tests and scripts.

## 3. Verification

The NVRAM clock was frozen for these runs. It follows host time, which would
otherwise make runs differ.

| test | result |
|---|---|
| *Alice in Wonderland*: save at frame 1800, run 900 more frames; load in a **new** machine (which had run 7 other frames) and run the same 900 | every picture, every audio sample and the CPU cycle count identical in all 900 frames |
| the same, loading back into the machine that kept running | identical |
| *Alice*: state saved from the `.cue`, loaded with the `.chd` | same disc id, 300 frames identical |
| state from the native core, loaded into the Python core | 20 frames identical |
| *Zelda: The Wand of Gamelon* (`.chd`): save at frame 3000, load in a new machine, 600 frames | identical; state 75 KiB |
| first picture after `--load-state` against the picture at `--save-state` | 0 of 368,640 pixels differ |
| *Zelda* state loaded with *Alice*, or with no disc | refused: "this state was saved with another disc (Alice_In_Wonderland.cue)" |
| damaged and junk files | refused with "is damaged (...)" / "is not an OpenCDi state file"; the game carries on unchanged |
| hotkeys under SDL's dummy video driver: F7, F5, F7, F8 (empty slot), F6, F8, pause + F8, Esc | "State saved to slot 2", "Slot 3 is empty", "State loaded from slot 2" (twice), back to the menu |
| launcher: Load state -> slot 2; Save state -> key 4 -> Enter | `('load', 2, ...)`, `('save', 4)` |

While finding the first mismatch, a comparison of the two machines' states
frame by frame showed one difference. The test had given the new machine a
different live pointer position than the saved one. This is the pointer
handling working as intended (see section 1). With the same live pointer the
runs are identical.

## 4. Tests

`tools/check_fixes.py`, 8 new checks (72 in all), without a BIOS. A test ROM
of seven instructions keeps writing the SCC68070 timer's count into RAM, so any
difference in timing after a load shows up in memory:

* a state continues exactly, in a new machine and in the running one (cycle
  count, PC, RAM and picture after 25 frames);
* the header and thumbnail can be read;
* a junk file, a cut file, a file with a device missing (fails in the middle of
  loading) and a file from another BIOS are all refused, and the machine's
  state is the same as before the attempt;
* the hotkeys are in the help text.

## Not verified

* **On a device:** the Android slot screen was not tried on a phone. The APK
  contains everything it needs: its Python has `_sha1`, `zlib` and `json`.
* **States from 0.1.6 in later versions:** the format has a version number
  (`format: 1`), and a newer format is refused with a message. An attribute
  added to a device later keeps its reset value when an older state is loaded.
