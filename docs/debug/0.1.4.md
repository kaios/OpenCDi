# OpenCDi 0.1.4 — debug notes

Changes between 0.1.3 and 0.1.4. For the debug log itself (location,
`--debug`, message format) see [0.1.1.md](0.1.1.md).

**Requested:** "build the apk for Android 10+".

This release adds an Android app. The desktop program behaves as before; the
changes it shares with the app are listed with **(desktop too)**.

---

## 1. Android build

**Files:** `android/buildozer.spec`, `android/main.py`, `android/manifest_app.xml`,
`android/README.md` (all new), `tools/build_apk.sh` (new)

* Built with python-for-android through buildozer, using the SDL2 bootstrap,
  Python, pygame, numpy, pyjnius and the `android` module. Targets Android 10
  and later (`minapi` and NDK API 29, target API 33), 64-bit ARM
  (`arm64-v8a`). Landscape, fullscreen, screen kept on while running.
* `tools/build_apk.sh` stages only the `opencdi` package and `main.py` into
  `android/build/src`, so no BIOS or other files from the source folder can end up in the app.
  It cross-compiles the native CPU core with the NDK's clang
  (`aarch64-linux-android29-clang`, same flags as the desktop build), records
  it in `prebuilt.json`, and runs buildozer. Output:
  `dist/opencdi-<version>-arm64-v8a-debug.apk`.
* The `.py` files are kept in the app (`android.no-byte-compile-python`),
  because the prebuilt core is matched to `m68k.py` by hash (item 4). If they
  are ever missing, the Android build trusts its own `prebuilt.json` anyway.
* **pygame 2.6.1 recipe** (`android/recipes/pygame`, `p4a.local_recipes`):
  python-for-android (v2026.05.09, master) builds Python 3.14.2, but its pygame
  recipe is pygame 2.1.0, whose Cython-generated C no longer compiles:
  `src_c/_sdl2/sdl2.c: fatal error: 'longintrepr.h' file not found`. The local
  recipe builds pygame 2.6.1, the version the desktop build is tested with. Its
  GitHub source has only the `.pyx` files, so it first runs pygame's own
  `setup.py cython_only` with the build machine's Cython 3.2.9 (3.1 or later
  supports Python 3.14).
* Build fixes along the way: buildozer only installs into a virtualenv
  when `VIRTUAL_ENV` is set (otherwise it tries `pip --user` and fails), and the
  NDK lookup must match the unpacked folder, not the downloaded `.zip`.

**Result:** `dist/opencdi-0.1.4-arm64-v8a-debug.apk`, 25.7 MB. Inspected:
* package `org.opencdi.opencdi`, version 0.1.4, `minSdkVersion` 29,
  target 33, native code `arm64-v8a` only;
* permissions READ/WRITE/MANAGE_EXTERNAL_STORAGE and WAKE_LOCK;
* contents: Python 3.14.2 with `_ctypes`, numpy 2.3.0, pygame 2.6.1
  (including `_sdl2`, mixer, font and its default font), pyjnius 1.7.0;
* `opencdi/native/_m68k_c6017aab6e35008d.so` is an ARM aarch64 ELF with its
  `prebuilt.json`;
* no BIOS, `.rom`, `.bin` or `.cue` files.

**Python 3.14 check:** the desktop Python 3.14.2 that python-for-android
builds for itself ran `tools/run_sst.py` with **0 failures on both cores**. The
C generated under 3.14 is byte-identical to the one from 3.11 (same library
hash), so the ARM library is built from exactly the code tested on the desktop.
* `android/main.py` sets `HOME` to the app's private folder, which holds the
  config, NVRAM and `debug.log`, sets `OPENCDI_ANDROID=1`, asks for storage
  access, then starts the normal launcher.

## 2. Storage access

**File:** `opencdi/android_support.py` (new)

* Android 11 and later: if the app is not yet allowed to manage all files, the system
  settings page for "All files access" opens on start. Android 10: the
  storage permission is requested, and the manifest sets
  `requestLegacyExternalStorage`.
* The launcher's file browser starts in shared storage (`/storage/emulated/0`)
  when it is readable, otherwise in the app's own folder
  (`Android/data/org.opencdi.opencdi/files`, readable without any permission).

**Debug log:** `INFO android screen WxH`, `INFO asked for all files access` or
`INFO asked for storage permission`, `WARNING storage permission request failed: ...`.

## 3. Touch controls and screen layout

**Files:** `opencdi/touch.py` (new), `opencdi/inputs.py` (`InputManager(touch=)`),
`opencdi/frontend.py` (`App`, `Emulator.draw`, `Emulator.run`),
`opencdi/launcher.py`

* Drag anywhere outside the buttons to move the CD-i pointer, like a touchpad;
  1 logical pixel is 1 pointer unit (`SPEED`). A tap shorter than 0.25 s that
  moved less than 12 pixels is a button 1 click lasting 6 frames. The **1** and
  **2** buttons are held while touched, and both together give "both
  buttons". **MENU** and the Android back button open the launcher.
* SDL's mouse copies of touches are ignored on the emulator screen, so a touch never
  "captures the mouse". The launcher still uses them: a tap selects, a
  second tap on the selected file opens it, and dragging scrolls the list.
* The window has one logical size for the whole run (`pygame.SCALED`):
  480 lines high, the height of an NTSC picture, and as wide as the screen's shape.
  The GPU scales it to the whole screen. The NTSC picture is drawn 1:1 in
  the middle. PAL pictures (560 lines) and the launcher canvas are scaled down to fit.
  A SCALED window is never resized: on the dummy driver, a second
  `set_mode` with SCALED failed with "failed to create renderer".
* Buttons: in the side margins when they are at least 110 logical pixels wide,
  as on phones (20:9 gives 149 pixels each side). Otherwise, as on 4:3 tablets,
  they are drawn see-through over the picture's right edge.

**Checked on the desktop** (dummy display, Android flag, faked screen size):
layouts for 2400x1080 and 2048x1536 rendered and inspected; picture
colours exact; drag, tap, held buttons, both buttons and MENU go through
`InputManager.update()` correctly. `check_fixes.py` has 6 touch checks.

## 4. Prebuilt native core record (desktop too)

**File:** `opencdi/m68k_native.py` (`sources`, `compile_command`, `inputs_digest`,
`write_prebuilt`, `_prebuilt`; command line `--sources DIR`, `--record DIR`)

Every build now writes `prebuilt.json` and `_m68k_<hash>.tables` next to the
library. The tables are the opcode tables in compressed form. The record holds a hash
of the files the core is made from (`m68k.py`, `m68k_native.py`, `core.c`,
`video.c`, `cycles070.bin`). While that hash matches, startup loads the
library and tables directly instead of generating all 65,536 handlers first:

| | before | now |
|---|---|---|
| loading the native core (desktop) | about 2 s | 0.1 s |

On a phone the difference is larger. If any of those files change, the
record no longer matches, and the core is generated and built again as in 0.1.3.
