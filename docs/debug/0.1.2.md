Changes between 0.1.1 and 0.1.2. For the debug log itself (location,
`--debug`, message format) see [0.1.1.md](0.1.1.md).

Verification done for this release:

* `tools/check_fixes.py`: 24/24 pass (4 new checks for this release).
* *CD-i Stub* (LGPL homebrew) booted with a `CDI/2352` cue sheet: the player

## 1. Cue sheets: `CDI/2352` and `CDI/2336` track types are accepted

**File:** `opencdi/disc.py`: `Disc._parse_cue`

**Symptom in 0.1.1:** selecting such a disc in the launcher showed
`Cannot use <name>.cue: unsupported track mode CDI/2352`.

**Cause:** the parser only matched `MODE<n>/<size>`. It did have a branch
meant to treat `CDI/...` as Mode 2, but it came *after* the pattern check that
had already rejected the line, so it could never run. `CDI/2352` and
`CDI/2336` are what many CD-i rippers write.

**Now:** the track type must be exactly one of `MODE1/<size>`,
`MODE2/<size>`, `CDI/<size>` or `AUDIO` (any letter case). `CDI` tracks are
read as Mode 2 with the given sector size, the same as `MODE2/2352` or
`MODE2/2336`. Anything else is still rejected, and the error message now
shows the track type as written in the cue sheet.

The old pattern also accepted track types that merely *started* with
`MODE<n>/<digits>` (for example `MODE3/2352` or `MODE1/2352X`). These are
now rejected instead of being silently misread.

**Debug log (DEBUG):** `<cue>: track NN is CDI/2352, 2352-byte sectors`, once per
track when a cue sheet is loaded with `--debug`.

**Check:** `check_fixes.py`, the "CDI/2352 cue", "CDI/2336 cue", "CDI/2336
sectors" and "unknown track mode" checks.

**Undo:** restore the `re.match(r'MODE(\d)/(\d+)', mode)` block in `_parse_cue`.

## 2. `tools/check_fixes.py` removes its temporary files

0.1.1's script left an `opencdi-check-*` folder in `/tmp` on every run.
It now deletes it on exit.
