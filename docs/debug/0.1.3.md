# OpenCDi 0.1.3 — debug notes

Changes between 0.1.2 and 0.1.3. For the debug log itself (location,
`--debug`, message format) see [0.1.1.md](0.1.1.md).

This release fixes two reported bugs: **the sound breaks up** (items 1-6) and
**the picture runs at about 30 fps** (items 7-11). Testing with a real title,
*Alice in Wonderland*, found three more: **a renamed disc image would not
load** (item 12), **the game ran at 28 of 60 fps** (items 13-15), and **video
lines were stretched by the CPU**, which made CD audio arrive too fast
(item 16). Item 17 changes the audio clock sync to match.

## The bug: sound breaks up

**Reported:** "The sound breaks up."

**Reproduced** with the real emulator window loop (dummy video, SDL's dummy
audio driver playing in real time), a 3-track test audio CD, and PLAY
pressed in the player menu. Over 30 s of CD playback:

| | fps during playback | audio dropouts | silent frames |
|---|---|---|---|
| 0.1.2 | 45.6–46.7 | 52–72 | 5.1–6.5 % |
| 0.1.3 (2 runs, 50 s each) | 47.3–48.1 * | **0** | 0 (after the CD starts) |

\* SDL's dummy audio driver runs about 2 % slow under load, and 0.1.3 now
follows the sound card's clock (item 3), so these runs paced themselves to
it. With a real sound card the emulator runs at the full 50.08 fps.

**Causes found (all five contributed):**

1. **No audio buffer.** 0.1.2 queued each frame's audio as its own short
   pygame Sound, with only one waiting behind the one playing (about 20–40 ms).
   CD-DA arrives as 0, 588 or 1,176 samples per frame (sectors come at 75 Hz,
   frames at 50 Hz), XA audio about 2,000 samples per sector. Any frame that
   was late by more than that left the mixer with nothing to play.
2. **The emulator was slower than real time during CD playback.** It
   averaged 21.2 ms per frame against a 20 ms budget, with frames up to
   47 ms. Drawing the picture took 8.3 ms of that, although during playback
   it almost never changes.
3. **Wrong frame rate.** The window loop paced at 50.0 fps (NTSC 59.94), but
   the emulated machine runs at 50.08 fps (NTSC 60.05). So audio was produced
   0.16 % slower than it plays, and any buffer would slowly run dry.
4. **Catch-up bursts.** After falling behind by up to 0.25 s, the loop ran
   frames back to back to catch up, pushing bursts of audio at the mixer.
5. **Clicks at every sector.** Each audio chunk was resampled on its own
   (37.8 kHz → 44.1 kHz with `np.interp`, 18.9 kHz with a 2× upsampler that
   restarted every sector), so chunk boundaries were not continuous.

## 1. New audio stream with a jitter buffer and feeder thread

**File:** `opencdi/frontend.py`: `class Audio`

* Audio is collected in a buffer and handed to the mixer in fixed 2,048-sample
  blocks (46 ms): one playing, one queued.
* Playback starts, and restarts after an underrun, only once 140 ms
  (`PREBUFFER`) is waiting. A late frame is absorbed rather than heard, and a
  real underrun becomes one clean pause rather than crackling.
* A **feeder thread** (`audio-feeder`) tops the mixer up every 5 ms
  (`FEED_INTERVAL`). Before this, a single slow frame could starve the mixer
  while 9,000 samples sat in the buffer.
* Rate correction: the audio is resampled by at most ±0.5 % (`DRC`) to keep
  the buffer near its target (`TARGET`, 140 ms) when clocks drift.
* While a sound is queued, the channel counts as playing. Between one sound
  ending and the queued one starting, pygame briefly reports "not busy";
  treating that as an underrun would have thrown away the queued block.
* When the sound stops (no new audio for 3 frames), the last partial block is
  padded with silence and played instead of being held back.
* Over 12 blocks (557 ms) buffered, for example while fast-forwarding with Tab,
  the oldest audio is dropped.

**Latency:** typically 150–200 ms from emulator to speaker (measured buffer
median 6,600 samples, maximum 8,550).

**Debug log:**
* `INFO audio: 44100 Hz, block 2048 samples, prebuffer 139 ms` at start.
* `INFO audio underrun #N (S samples buffered); refilling 139 ms before restarting`
  is an audible gap. The first 20 are logged, then every 100th.
* `DEBUG audio buffer over 24576 samples; dropped the oldest N` (normally
  only during fast-forward).
* `INFO session: F frames, P pictures skipped; audio B blocks, U underruns, D samples dropped`
  is written each time you leave the emulator screen (Esc or quit).
  **Start here when sound problems are reported:** underruns above 0 mean the
  host could not keep up.

**Tuning:** if underruns persist on a slow machine, raise `PREBUFFER` and
`TARGET` (more latency, fewer gaps). On a fast machine they can be lowered to
2 blocks for less latency.

**Undo:** restore `class Audio` and the audio lines in `Emulator.run` from
tag v0.1.2.

## 2. Seamless resampling

**Files:** `opencdi/audio.py` (new: `LinearResampler`), `opencdi/machine.py`
(`audio_out`), `opencdi/cdic.py` (`play_audio_sector`)

A streaming resampler carries its read position and last sample from one
chunk to the next, so its output is bit-identical whether the input comes in
one piece or many. The machine keeps one per source rate. The CDIC now
passes 18.9 kHz XA audio straight to it; the per-sector `_upsample2` is gone.

**Debug log (DEBUG):** `audio source rate 37800 Hz -> 44100 Hz` when the
source rate changes, and `audio output not collected; oldest chunks dropped`
if nothing reads the machine's audio for 64 chunks.

**Check:** `check_fixes.py`, "resampler seamless across blocks" (3 rates).

## 3. Frame pacing: exact frame rate, sync to audio, no catch-up bursts

**File:** `opencdi/frontend.py`: `Emulator._emulate_loop` (was `Emulator.run`, see item 7); `opencdi/machine.py`: `Machine.frame_rate`

* Paces at `Machine.frame_rate()`, which is clock / (lines × 960 cycles):
  50.08 Hz PAL, 60.05 Hz NTSC. It is recomputed every frame, because the ROM
  can switch the timing.
* **Sync to audio:** when more than `TARGET + BLOCK` samples are buffered, the
  next frame waits for the sound card (up to one frame period). Emulation speed
  then follows the sound card's real clock and audio never piles up. In testing
  this brought audio dropped for overflow from 74,478 samples to 0.
  *Replaced by a smoother two-way sync in item 17.*
* When the loop falls behind by more than 2 frames it resets its schedule
  instead of catching up (0.1.2: 0.25 s).

## 4. Frame skipping when behind

**Files:** `opencdi/frontend.py` (`Emulator.run`), `opencdi/machine.py`
(`run_frame(render=...)`), `opencdi/mcd212.py` (`skip_render`)

If a frame finishes more than a whole frame late (half a frame before the
frame-rate fix, item 7), the *picture* of the next frame is not drawn: no rendering and no window update. The frame is still
emulated in full, so sound and game speed are unaffected. At most 3 frames in
a row are skipped, then one is always drawn. Fast-forward never skips.

**Debug log:** the window title shows `N skipped` per second. With `--debug`,
`DEBUG <fps> fps (<speed>%), N of M pictures skipped, audio buffer S samples`
is logged every second while skipping or below 98 % speed. The `session` line
gives the totals. Skipping is normal during the ROM boot; skipping during play
means the machine is near its limit.

## 5. Frame cache: unchanged pictures are not rendered again

**File:** `opencdi/mcd212.py`: `render_frame`, `frame_signature`, `used_plane_bytes`, `PlaneLine.vend`

When a frame's decoder state and the plane bytes the picture actually reads are
the same as last time, the previous picture is reused; the cursor is still
drawn fresh. The comparison covers only the bytes the picture reads (each
line's start to end). OS-9 keeps its variables in plane A memory and changes
them every frame, so comparing all of plane memory would almost never match:
that was a 9 % hit rate on the first try, against 97 % now.

**Measured:**
* Cache hits during CD playback: 1,550 of 1,600 frames. Every hit was checked
  against a full render of the same frame, and all 1,550 were identical.
* Headless speed: boot 41 → 58.5 fps; *CD-i Stub* disc 57 → 88.6 fps.
* Boot and *CD-i Stub* screenshots are pixel-identical to 0.1.2.

**Debug log:** `INFO video: R pictures rendered, C reused unchanged, S skipped` per session.

**If a picture ever looks stale** (an update not shown): set
`self._cache_out = None` at the top of `render_frame` to disable the cache,
and report what was on screen. The cache is cleared on every video reset
because the CLUT/matte version counters restart there.

**Check:** `check_fixes.py`: "frame cache reuses / ignores / re-renders",
"frame skip keeps the previous picture".

## 6. Tests (sound)

New checks in `tools/check_fixes.py` for the sound fix:
* resampler seamlessness at 3 rates;
* a simulated sound card on an exact clock, with CD-DA delivered per frame and
  every 47th frame 70 ms late: 0 gaps with the feeder thread. The same run
  without the feeder finds 31 gaps, which shows the test can catch the bug;
* frame cache reuse, re-render, unrelated memory, and frame skip.
* `Audio(channel=..., feeder=False)` is the test hook that makes this possible.

## The bug: the picture runs at about 30 fps

**Reported:** "The framerate is 30fps. Make it 60fps, else it looks really bad."

**Reproduced** in the real window on this machine's display, which is
`localhost:10.0`: SSH X forwarding to a 60 Hz monitor (1920x1080). In the test
the pointer circled the player menu and a bar moved every frame, so every
picture differed, as in an animated game:

| | emulated | shown in the window |
|---|---|---|
| 0.1.2 (PAL, menu) | 40.1 fps of 50 | 40.1 fps |
| 0.1.2 (PAL, audio CD screen) | 41.1 fps of 50 | 41.1 fps |
| 0.1.3, PAL | 50.1 fps | 49.8 fps |
| 0.1.3, NTSC (new default), menu | **60.1 fps** | **58.0 fps** |
| 0.1.3, NTSC, audio CD screen | **60.0 fps** | **56.2 fps** |

A larger window or a busier picture made 0.1.2 slower still, which matches the
reported 30.

**Causes found:**

1. **Each picture has to cross the network.** Over X forwarding, SDL sends
   the whole window as raw pixels every time it updates the screen. MIT-SHM
   (shared memory) does not work, and updating only part of the window doesn't
   help either. Measured on this link: 15.6 ms for 768x480, 18 ms for 768x560,
   and 68 ms for a 1536x1120 window (`--scale 2`). The cost grows with the
   window's pixel count, whichever SDL renderer is used (software, OpenGL,
   OpenGL ES).
2. **Emulation and display took turns.** 0.1.2 emulated a frame, then sent it
   and waited, then emulated the next. 13 ms of emulation plus 18 ms of sending
   is about 31 ms a frame, roughly 30 fps.
3. **The machine was a PAL player.** PAL CD-i video is 50 Hz. On a 60 Hz
   monitor, 50 pictures a second cannot be spread evenly, so even at full speed
   motion judders.
4. **The window was 768x560 for a 768x480 NTSC picture**, sending black
   borders and scaling every frame.

## 7. Emulation runs on its own thread

**File:** `opencdi/frontend.py`: `Emulator` (`_emulate_loop` on the
`emulation` thread, `run` on the main thread)

* The emulation thread runs the machine, paced at its frame rate and synced to
  the sound card exactly as before (items 3 and 4). It reads input once per
  emulated frame, so pointer speed does not depend on the display.
* The main thread handles window events and puts the newest picture in the
  window. pygame releases the GIL while the picture is sent, so the
  emulation keeps running meanwhile. Python test: a thread running Python
  code kept 78-89 % of its speed while the window was being updated.
* If the display is slower than the emulation, the display shows the newest
  picture and skips the ones it missed. Emulation and sound are not slowed.
* **Thread switch interval** 1 ms while the emulator runs (`SWITCH_INTERVAL`;
  Python's default 5 ms is restored on exit). Each time a picture has been
  sent, the main thread has to wait for the GIL. At 5 ms that wait was a third
  of a 60 Hz frame: 57.0 fps shown before, 58.0 fps after.
* **Frame skip threshold** raised from half a frame late to a whole frame. With two
  threads, short delays are normal and are made up on the next frame without
  dropping a picture.
* An exception on the emulation thread is re-raised on the main thread, so it
  still ends up on screen and in the debug log.

**Undo:** restore `Emulator.run` from 0.1.3's sound fix (both in one loop);
everything else keeps working.

## 8. Pictures that did not change are not sent

**File:** `opencdi/frontend.py`: `Emulator.run`

If the new picture is identical to the one in the window, nothing is sent.
Comparing takes about 0.4 ms; sending takes about 16 ms over SSH. In the
player menu with the audio CD, 2,198 of 2,247 pictures were unchanged.
The window is redrawn anyway after it is uncovered, resized or switched to
fullscreen.

## 9. 60 Hz by default; the window fits the picture

**Files:** `opencdi/launcher.py` (`use_ntsc`), `opencdi/__main__.py`
(`--ntsc`, new `--pal`), `opencdi/frontend.py` (`App.set_content_size`)

* The player now starts as an **NTSC player (60.05 Hz, 768x480)**. 0.1.2
  defaulted to PAL (50.08 Hz, 768x560). The cdi220b ROM accepts either. In
  NTSC mode the player menu and *CD-i Stub* boot and work, and the CPU work per
  second barely changes: about 15.1 million cycles a second either way.
* **If you chose PAL** under Video in the launcher, that choice is saved in
  `config.json` and kept. `--pal` and `--ntsc` set it from the command line.
* The emulator window now takes the size of the picture times `--scale`:
  768x480 in NTSC. It no longer sends a black border or scales each frame. If
  you resize the window yourself, your size is kept. The launcher still uses its
  768x560 layout.
* When the window is exactly the picture's size, the picture is copied
  straight into it, with no extra copy or scaling.

**Over SSH, keep `--scale 1` and don't go fullscreen.** Every window pixel is
sent each frame: a 1536x1120 window costs 68 ms a picture (about 15 fps
shown). Emulation and sound stay at full speed either way.

## 10. Faster video timing code

**File:** `opencdi/mcd212.py`

The per-line video code was 40 % of the emulation time. Three changes:

* `plane_line` keeps each plane's decoder state (mode, file type, mosaic,
  transparency, CLUT/matte versions, screen width) until a register changes.
  `state_ver` counts every register write, whether from the CPU (`_write`),
  from ICA/DCA programs (`set_register`, `set_display_parameters`), or a matte
  update.
* `process_dca` decodes each 64-byte DCA block once and replays its actions
  while the block's bytes stay the same (`_decode_dca`, `_dca_cache`).
* The ICA program reads each command word with one `struct` call from the
  frame's snapshot. `used_plane_bytes` joins consecutive lines as it goes.

**Measured** (headless, NTSC, this machine):

| | before | after |
|---|---|---|
| audio CD player screen | 13.6 ms per frame | 12.2 ms |
| *CD-i Stub* | 4.8 ms per frame | 3.9 ms |

**Identical output:** the old and new code were run side by side for 1,500
frames each: PAL and NTSC, with no disc, with *CD-i Stub*, and with the audio
CD (PLAY pressed). Every frame hash, the audio stream and the cache counts
matched in all six runs.

**If something on screen stops updating after a register change**, suspect a
state change that does not bump `state_ver`. Setting `self._pl_state = [None,
None]` at the top of `frame_start` disables the cache.

## 11. Tests and debug log (frame rate)

New checks in `tools/check_fixes.py` for the frame-rate fix (52 checks in all now, including items 12-16):
* plane decoder state follows CPU and ICA/DCA register writes;
* the DCA block cache re-decodes a block whose bytes changed;
* video defaults to NTSC and a stored PAL choice is kept;
* the emulation thread runs frames, shows them in order, and quits cleanly;
* an error on the emulation thread reaches the main thread; the thread stops
  and the switch interval is restored.

**Debug log:**
* `INFO display: N pictures sent to the WxH window (T ms each), U unchanged
  not sent, M missed (display too slow)` each time you leave the emulator
  screen. **Start here when the picture is not smooth:** T near or above
  16 ms means the display link is the limit (use a smaller window), and M above
  0 counts pictures the display never showed.
* With `--debug`, once a second when frames are lost or the speed drops below
  98 %: `DEBUG <fps> fps (<speed>%), N pictures not shown (S skipped, M missed
  by the display), K sent, audio buffer B samples`. *Skipped* means the host
  CPU was behind; *missed by the display* means sending pictures was too slow.
* `DEBUG window WxH for a WxH picture` when the window is resized to fit.
* The window title shows the emulated frame rate. `N not shown` there means
  pictures were skipped or missed in that second.

## The bug: Alice in Wonderland runs at 28 of 60 fps

**Found** while testing the frame-rate fix with *Alice in Wonderland*.
In its animated scenes every frame changes, and the emulator managed 28 fps
headless: 36 ms per frame against a 16.7 ms budget. Of that, 22 ms was the
68000 emulated in Python and 14 ms was drawing the picture (both planes are
DYUV). The emulated CPU alone needed more than real time, so PAL would not
have helped: PAL needs the same CPU work per second.

## 13. Native CPU core

**Files:** `opencdi/m68k_native.py` (new), `opencdi/native/core.c` (new),
`opencdi/machine.py` (`create_cpu`), `tools/build_deb.sh`, `tools/run_sst.py`

* The 1,851 instruction templates that `m68k.py` generates as Python are
  translated to C with Python's `ast` module, and so are the runtime helpers
  (flags, shifts, BCD, exception entry, interrupts, RTE). The translator handles
  only the constructs the templates use; anything else raises `Unsupported`.
  The semantics come from the same source as the Python core.
* Hand-written in `core.c`: the run loop, the bus error frame, and memory
  access. They mirror `run()`, `bus_error()` and the bus functions
  line by line, including which exceptions are caught where, using
  `setjmp`/`longjmp`. All values are `int64_t` built with `-fwrapv`, which
  matches Python's integers for what the handlers compute.
* RAM and ROM are read and written directly in the bus's own bytearrays, so
  there is no copying, and DMA from Python devices is seen at once. Device
  registers go back to Python through `ctypes` callbacks; a Python exception
  there becomes the same guest bus error or crash as before.
* `ctypes` releases the GIL while the core runs, so the emulated CPU no longer
  takes turns with the window thread.
* The library is compiled with the system C compiler the first time it is
  needed, taking about 15 s, and is cached as `_m68k_<hash>.so` in
  `opencdi/native/`, or in `~/.cache/opencdi/` if that is not writable. The
  hash covers the generated code, so a changed `m68k.py` gets a new build. The
  `.deb` contains the build and is now made per architecture
  (`opencdi_0.1.3_amd64.deb`).
* **Fallback:** without a C compiler, or with `OPENCDI_CPU=python`, the
  Python core runs as before, and a message says so. `cpu.ns` works with both
  cores, so tools and tests drive either one.

**Verified:**
* **SingleStepTests**, all 127 files: 0 failures, the same as the Python
  core (`tools/run_sst.py`; `OPENCDI_CPU=python` runs the Python core). The
  first native run failed MOVEQ: its constant did not fit the 32-bit argument
  table. Fixed by making the table 64-bit.
* **The same run on both cores, frame by frame:** every picture and the whole
  audio stream are identical on boot, *CD-i Stub*, the audio CD (PAL and NTSC,
  1,500-3,000 frames each), and *Alice in Wonderland* (3,000-3,600 frames).
  For these comparisons the NVRAM clock was frozen to emulated time: it
  follows the host clock, and the slower Python core sees the seconds tick at
  different frames. Unfrozen, that gave one false 2-frame difference.
* `check_fixes.py` runs the CPU checks (LINK, trace, budget accounting,
  IndexError logging) on both cores.

**Speed** (headless, NTSC, *Alice in Wonderland* animated scenes): the
68000 went from about 22 ms to about 3 ms per frame, callbacks included.

**Debug log:** `INFO native CPU core loaded from <path>` at start, or
`WARNING native CPU core not available, using the Python core: <reason>`.
A failed build adds `WARNING could not build the native CPU core in <dir>`
with the compiler's error output. **Check this first if a machine is suddenly
slow.**

## 14. Native DYUV decoding and plane mixing; bulk CD DMA

**Files:** `opencdi/native/video.c` (new), `opencdi/mcd212.py`
(`native_lib`, `render_dyuv`, `mix`), `opencdi/cdic.py` (`dma_transfer`)

* `vid_dyuv` decodes DYUV lines and `vid_mix` mixes the two planes (after the

* A CDIC DMA transfer that stays inside one 64 KiB RAM page, and does not wrap the

**Verified:** pictures identical to numpy, by the comparisons in item 13
(the Python side there runs the numpy code). The DMA path was checked against
a copy of the code from before these changes: 3,000 frames of *Alice*, plus
*CD-i Stub* and the audio CD, all identical. New checks compare the slice copy
with the word loop at three addresses, including a transfer that crosses a page.

## 16. Video lines were stretched by the CPU

**File:** `opencdi/machine.py`: `Machine.run_frame` (`_line_t`),
`opencdi/cdic.py`: `sector_tick`, `audio_tick`

**Symptom:** at full speed with sound, *Alice* still ran at only 51-52 fps
(86 %). The audio buffer stayed full and the sync to the sound card held
emulation back. The machine was producing more audio per frame than it
should.

**Cause:** each line ran to `now + 960` cycles, counted from wherever the CPU
had stopped. An instruction that runs past the end of a line makes `now`
overshoot, and that overshoot was added to every line, so frames came out
too long. Measured in *Alice*: 255,000-308,000 cycles per frame instead of
251,520 (up to 22 % longer), because its long `movem` copies overrun almost
every line. Video timing therefore ran slow against the CPU and the CD
drive, so emulated time, CD sectors and audio ran up to 22 % fast against
the 60 Hz frame pacing. The player menu was affected less: about 1 %.

**Now:** lines start every 960 cycles on a fixed timeline (`_line_t`), and
an overrun only shortens the next line. Frames are exactly 251,520 cycles;
measured in *Alice*: 251,519-251,535. The CD drive's 75 Hz sector and audio
ticks are kept on a fixed timeline in the same way, instead of being
rescheduled from the time they ran.

**Effect:** games now get the right number of video frames per second of CPU
time, and audio arrives at the real rate, measured at 43,500-44,700 samples per
emulated second. This may well have been part of "the sound breaks up" in
games.

**Check:** `check_fixes.py`: "frames keep their length when the CPU overruns
lines" (a fake CPU that overruns every slice by 150 cycles) and "CD sector
ticks stay at 75 per second" (every event 400 cycles late). Both fail with the
old code.

**Debug log (DEBUG):** `line timing N cycles behind; resynchronised` if the
CPU ever gets more than 1,000 lines behind, which should not happen.

## 17. Audio clock sync in both directions, on the average buffer level

**File:** `opencdi/frontend.py`: `Emulator._emulate_loop`
(`SYNC_SMOOTH`, `SYNC_GAIN`, `SYNC_RANGE`, `SYNC_QUIET`)

With item 16 the emulator produces audio at exactly the real rate. SDL's dummy
audio driver turned out to play 4.7 % fast (46,160 samples a second), so the
buffer ran dry: 10 underruns in the audio CD test, because item 3 could only
slow emulation down. Item 3 also reacted to the instantaneous buffer level,
and XA audio arrives in bursts of up to 9,400 samples, so its pacing would jerk.

**Now:** the buffer level is averaged over about 2 s, and each frame is
made up to 10 % longer or shorter according to how far that average is from
the target. The sync applies only while audio is playing, so the end of a sound
does not speed anything up. If the buffer is about to overflow, the next frame
still waits a whole frame. With a real sound card the adjustment stays close to
zero.

**Measured** (audio CD, dummy driver): 0 underruns, 0 samples dropped, and
the emulator follows the driver's fast clock at 62.3 fps. *Alice* on the real
window with sound: 61.0-61.4 fps, 0 underruns, 0 dropped.

**Frame pacing on this SSH display:** median frame interval 16.2-16.4 ms;
1.5 % of intervals are over 25 ms. This is CPU contention on this 2-core
machine (`sshd` encrypts every picture sent): emulation work per frame is
10 ms here against 6 ms headless.

## Not verified

* **A local display.** The frame-rate tests used the SSH-forwarded display
  this machine has. A local display has no network in between, so sending a
  picture costs far less and the same code should have more headroom.
* **Other commercial titles.** Only *Alice in Wonderland* was tested,
  and only its first few minutes, without interacting with the game. CD-i
  discs are made to work on both PAL and NTSC players; a title that misbehaves
  in NTSC can be switched to PAL in the launcher.
* **Other architectures.** The native core was built and tested on amd64
  with gcc 12. The C has no architecture-specific code, but other machines
  are untested; they fall back to the Python core if the build fails.

* **Real sound card.** These tests used SDL's dummy audio driver. Playing
  test tones through this machine's speakers wasn't wanted, so real hardware
  is the remaining check. If sound still breaks up on a real card, send the
  `session:` and `audio underrun` lines from `~/.opencdi/debug.log`.
* **XA ADPCM in a real title** was checked only with the dummy sound driver
  (*Alice in Wonderland*: 0 underruns, audio at the real rate), never heard
  through speakers.
