# OpenCDi 0.1.5 — debug notes

Changes between 0.1.4 and 0.1.5. For the debug log itself (location,
`--debug`, message format) see [0.1.1.md](0.1.1.md).

**Requested:** "make sure it also supports CHD files".

## 1. CHD disc images

**Files:** `opencdi/chd.py` (new), `opencdi/disc.py` (`Disc._chd_tracks`,
`read_raw`), `opencdi/launcher.py` (`DISC_EXT`), `opencdi/__main__.py` (help text)

MAME CHD files, version 5 (what `chdman createcd` makes), open in the launcher
and on the command line like `.cue` files, on the desktop and on Android.

* **Format** (as MAME's `chd.cpp` / `cdrom.cpp` and libchdr): the v5 header;
  the compressed hunk map (MAME's RLE-coded Huffman tree, then RLE of hunk types,
  then lengths, offsets and CRCs, checked against the map CRC); CHT2/CHTR track
  metadata; hunks of 2448-byte frames (2352 bytes of sector, 96 of subcode).
* **Hunk types:** compressed (codec slot 0-3), uncompressed, and "copy from
  self". Every hunk is checked against its CRC-16. Hunks that refer to a parent
  CHD are refused with a message.
* **CD codecs:**
  * `cdlz`: LZMA sectors (lc=3 lp=0 pb=2, dictionary sized as LZMA's level 9
    for the hunk) and Deflate subcode;
  * `cdzl`: Deflate for both;
  * `cdfl`: FLAC sectors (bare FLAC frames, stereo, block size 1176), then
    Deflate subcode from where the FLAC data ends;
  * `cdzs`: Zstandard for both, when a zstd module is present (Python 3.14's
    `compression.zstd`, or the `zstandard` or `pyzstd` packages).
* **ECC:** sectors that chdman stored without their sync pattern and ECC
  (one flag bit per frame) get both back. P and Q parity are computed as in
  `cdrom.cpp` (`ecc_generate`; header bytes count as zero for Mode 2), with
  numpy.
* **Tracks:** every track starts on a multiple of 4 frames in the CHD. A
  pregap counts in disc addresses, and a pregap of type `V...` is stored in
  the image and can be read (from a `.cue`, those sectors also come from the file).
  CHD stores audio big-endian, and it is swapped back to the byte order of `.bin`
  images.
* **Not supported, with a message:** CHD versions 1-4 ("convert it with
  `chdman copy -i old.chd -o new.chd`"), parent CHDs, GD-ROM (`CHGD`) and
  hard disk CHDs, and `cdzs` without a zstd module.

**Debug log:** `INFO <file>: CHD v5, N hunks of B bytes, codecs ..., T tracks`
when a CHD is opened; `DEBUG <file>: track N is TYPE, F frames from LBA L` with
`--debug`.

## 2. Native FLAC and LZMA decoders

**Files:** `opencdi/native/flac.c`, `opencdi/native/lzma.c` (new),
`opencdi/flac.py` (new), `opencdi/m68k_native.py` (`NATIVE_C`), `tools/build_apk.sh`

* `flac_decode_cd()`: a FLAC frame decoder (constant, verbatim, fixed and LPC
  subframes; Rice and Rice2 residuals with escapes; wasted bits; left/side,
  side/right and mid/side). It writes big-endian samples, the way CHD stores
  them. `flac.py` is the same in Python: the reference and the fallback.
* `lzma_decode_raw()`: a raw LZMA1 decoder written from the public-domain
  LZMA specification decoder. **The Android Python has no `lzma` module**
  (the app's bundle has only `zlib`), so without it the most common CHD codec
  would not work in the app. On the desktop it is used too when the native
  library is loaded, and Python's `lzma` is the fallback.
* Both are compiled into the same library as the CPU core. `NATIVE_C` lists
  every C file, so the hash, the desktop build and the Android cross-compile
  (`"$GEN"/*.c`) all take the same files.

| speed (this machine) | Python | native |
|---|---|---|
| FLAC hunks (noisy data, all-FLAC CHD) | 326 sectors/s | 26,672 sectors/s |
| LZMA hunk | 687 µs (Python's lzma) | 739 µs |

A CD player needs 75 sectors a second.

## 3. Verification

Test images made with `chdman` 0.251 (Debian package `mame-tools`) from the
disc images used before:

| image | content | result |
|---|---|---|
| *Alice in Wonderland* (default codecs) | 261,115 sectors, 23,132 LZMA + 9,508 Deflate hunks | every sector identical to the `.bin` |
| the same, every LZMA hunk | C decoder vs Python's `lzma` | 23,132 of 23,132 identical |
| first 20,000 sectors, `-c cdfl` (FLAC on data) | native and Python FLAC | identical (Python: first 400 sectors; native vs Python on 40 random hunks) |
| first 20,000 sectors, `-c cdzl`, `-c cdlz`, `-c none`, `-hs 4896`, `-hs 39168` | Deflate, LZMA, uncompressed, 2- and 16-frame hunks | all identical |
| audio CD, 3 tracks | 526 copy-from-self, 5 LZMA, 32 FLAC hunks | identical |
| *CD-i Stub* | | identical |
| synthetic: Mode 1 + audio with an `INDEX 00` pregap | ECC regenerated for all 301 Mode 1 sectors, stored pregap | identical |
| synthetic: audio with `PREGAP` + Mode 2 | unstored pregap, 777-frame track (padding), ECC for all 136 form 1 sectors | identical |

ECC: chdman strips ECC only from sectors whose ECC it verifies. So the
regenerated count matching exactly the sectors made with ECC by `ecc_generate`
(437) shows that the two agree.

**Emulator:** *Alice in Wonderland* from the `.chd` and from the `.cue`,
3,000 frames: every picture and the audio identical, at the same speed
(7.4 against 7.7 ms per frame).

**Zstandard:** chdman 0.251 cannot write `cdzs`. `tools/chd_writer.py`, a
small CHD writer for tests, wrote it, and every sector read back exactly with
the `zstandard` package (0.25.0).

**chdman 0.251 bug found on the way, not in OpenCDi:** with a cue sheet
whose first `FILE` has two tracks and a second `FILE` follows, chdman records
the last track of the first file 301 frames too long, the length of the
file's first track. With two tracks in the second file as well, it fails
("Input/output error"). OpenCDi reads what the CHD says; one track per file is
safe.

## 4. Tests

`tools/check_fixes.py`: 64 checks (6 new), none of which need chdman:

* FLAC: a small encoder in the test makes fixed-predictor, Rice-coded frames
  (independent and mid/side); the Python and the native decoder must return
  the samples exactly and stop at the same byte.
* CHD (`cdzl`, `cdlz`, and `cdzs` if a zstd module is present), written
  by `tools/chd_writer.py`: compressed, uncompressed and copy-from-self hunks,
  ECC removed from Mode 1 and Mode 2 form 1 sectors, three tracks with padding,
  audio. Every sector must read back as in the `.bin`, the track layout must
  match, and ECC must be rebuilt for exactly the 49 stripped sectors.
* The error messages for a version 4 CHD and for a file that is not a CHD.

## Not verified

* **Zstandard CHDs made by a real chdman** (0.263 and later): only CHDs from
  the test writer were read.
* **On Android:** CHD support is in the 0.1.5 APK, built like 0.1.4 and not
  run on a device yet. `cdzs` does not open there: the app's Python has no zstd
  module.
* **CHDs with subcode** (`SUBTYPE:RW`): read like the others, and the emulator
  does not use subcode.
