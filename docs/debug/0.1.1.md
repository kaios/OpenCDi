# OpenCDi 0.1.1 — debug notes

Every change made between 0.1.0 and 0.1.1, with what it does, how it was
checked, what it writes to the debug log, and how to undo it if it turns out
to cause trouble.

## The debug log

* File: `~/.opencdi/debug.log`, rewritten on every start.
* Warnings (emulator faults, unexpected guest behaviour) are always written.
* Start with `--debug` to also get the per-event `DEBUG` messages listed below.
* Module: `opencdi/debuglog.py`. Each subsystem logs under its own name
  (`opencdi.machine`, `opencdi.cdic`, `opencdi.scc68070`, `opencdi.slave`,
  `opencdi.disc`, `opencdi.mcd212`).

Quick regression check for everything below (no BIOS needed):

```sh
tools/check_fixes.py          # 20 checks, exits non-zero on failure
tools/run_sst.py DIR          # SingleStepTests/m68000 v1 data in DIR
```

Verification done for this release:

* `tools/check_fixes.py`: 20/20 pass.
* SingleStepTests 68000 suite, all 127 files: 0 failures, results identical
  file by file to the 0.1.0 core.
* Headless boot with `cdi220b.rom`, 400 frames: the player menu screenshot is
  pixel-identical to 0.1.0, and speed is the same (41–42 fps for both on the
  test machine).
* The GUI loop was driven with a dummy video driver: it runs, opens the menu
  and offers Resume.

---

## 1. CPU: trace mode (T bit) is emulated

**File:** `opencdi/m68k.py`: `set_sr`, `run`

**Before:** the trace bit in SR was stored but did nothing.
**Now:** while T is set, each instruction is followed by a trace exception
(vector 9). Writing SR with T set breaks out of the fast loop, and the loop
then single-steps until T is clear again, normally on the RTE that leaves
the trace handler. The fast loop itself is unchanged, so there is no cost
when trace is off.

**Debug log:** `opencdi.machine: trace exception after pc=XXXXXXXX op=XXXX`
(DEBUG, once per traced instruction).

**Switch:** `cpu.ns['TRACE'] = False` turns it off. `tools/run_sst.py` does
this, because the test data records the state *before* the trace exception.

**Undo:** in `run`, remove the `if srh & 0x8000 and TRACE:` block and its
`continue` in the `CpuBreak` handler, and make `set_sr` return `irq_pending()` only.

## 2. CPU: instructions that break out of the fast loop now count their cycles

**File:** `opencdi/m68k.py`: `run`, `except CpuBreak`

**Before:** an instruction that raised `CpuBreak` (SR write that unmasks a
pending interrupt, STOP) skipped `left -= CYC[op]`. The loop then ran
one instruction past its budget and the reported cycle count was short.
**Now:** its cycles are counted before the pending interrupt is examined.

This surfaced while testing item 1. It affects timing only slightly
(one instruction per such event), but it is now exact.

**Check:** `check_fixes.py`, "SR write counts as the whole budget step";
SingleStepTests `MOVEtoSR`, `ANDItoSR`, `ORItoSR`, `EORItoSR`, `RTE`, `STOP`.

**Undo:** delete the `left -= CYC[op]` line at the top of the `CpuBreak` handler.

## 3. CPU: `IndexError` faults are logged with a traceback

**Files:** `opencdi/m68k.py` (`run`, `except IndexError`) and
`opencdi/machine.py` (`Machine._log_fault`)

**Before:** any Python `IndexError` raised while the CPU was running,
including one from device code, silently became a guest bus error.
**Now:** the guest still sees a bus error, but the full Python traceback is
written to the log, so an emulator bug can no longer hide as a guest crash.
Logging stops after 50 faults so a guest that keeps faulting cannot fill the disk.

**Debug log:** `WARNING opencdi.machine: IndexError at pc=... op=... turned into a bus error`
followed by the traceback (always written, no `--debug` needed).

**What to do with it:** any of these warnings is an emulator bug. The last
frame of the traceback names the device and line.

## 4. SLAVE: input buffer overflow fixed

**File:** `opencdi/slave.py`: `Slave.slave_w`

**Before:** some command sequences wrote past the 17-byte input buffer.
One example is command `0x80` on port 3 followed by data on port 0. The
resulting `IndexError` became a guest bus error (see item 3). Confirmed with
the 0.1.0 code.
**Now:** the partial command is dropped and the buffer is cleared.

**Debug log:** `WARNING opencdi.slave: input buffer overflow (offset N, data XX, buffer ...); command dropped`.
If a title shows this, the buffer dump shows which command the SLAVE
emulation does not understand yet.

## 5. SCC68070 timer 0: writing the reload register no longer restarts the timer

**File:** `opencdi/scc68070.py`: `_write16m`, timer registers

**Before:** a write to the reload register (`0x80002022`) restarted timer 0
from the value it had at its last overflow, losing the time already counted.
Byte writes to the counter merged with that stale value too.
**Now:** reload only stores the value used at the next overflow (as in MAME).
A counter write merges with the live count, then restarts the timer from it.

**Debug log (DEBUG):** `timer0 reload=XXXX (count XXXX keeps running)` and
`timer0 count set to XXXX`. In a normal boot the ROM writes each once.

**Symptom if wrong:** OS-9 tick rate drift. Clock or animation speed would be
off, or the system tick would stall.

**Undo:** put `self.set_timer()` back after the reload write, and use
`comb(self.timer0)` for the counter.

## 6. Disc images: byte-swapped raw images are read correctly, audio tracks included

**File:** `opencdi/disc.py`: `Disc._detect_byteswap`, `Disc.read_raw`, `_single_file_track`

**Before:** `Disc.byteswapped` was always False. The CDIC un-swapped data
sectors itself, but skipped that check for CD audio, so the audio on a
swapped image played as noise. Mode 1 detection also failed on swapped single files.
**Now:** the first sector of the first raw data track decides. If its sync
pattern is byte-swapped, every 2352-byte sector of the image is swapped back
on read, audio included. The CDIC's own swap detection stays as a fallback
and never triggers for these images.

**Debug log:** `INFO opencdi.disc: <path>: byte swapped raw image; ...` once per disc.

**Limitation:** an audio-only image has no sync pattern, so swapping cannot
be detected there. An image whose data track is swapped but whose audio
tracks are not would now play its audio swapped. No dumper is known to
produce such images.

## 7. CDIC: audio volume (attenuation)

**File:** `opencdi/cdic.py`: `DEFAULT_ATTEN`, `reset`, `attenuate`, `play_cdda_sector`;
`opencdi/machine.py`: `Machine.reset`

* Default after reset is now straight stereo (`L→L ff, L→R 00, R→R ff, R→L 00`).
  0.1.0's constructor set this value, but `reset()` then replaced it with
  `ff ff ff ff`, which mixed both channels into both speakers at double level
  until the ROM set the volume.
* CD-DA now goes through the same volume matrix as ADPCM audio. Before, it
  ignored the SLAVE volume completely.
* `muted` is cleared on a full machine reset (power-on, F3, SLAVE reset
  command). It is **not** cleared by the 68000 `RESET` instruction, which
  only resets peripherals.

**Debug log (DEBUG):** `attenuation LL=.. LR=.. RR=.. RL=..` each time the SLAVE sets it.

**Symptom if wrong:** CD audio volume differs from 0.1.0. If a title sets
volume 0 and expects CD-DA to still play, `attenuate()` is where to look.

## 8. CDIC: DMA transfers leave the channel in its "finished" state

**File:** `opencdi/cdic.py`: `CDIC.dma_transfer`

**Before:** only the memory address counter was advanced.
**Now:** the device address counter advances too, the transfer counter is
set to 0, CSR bit 7 (COC, channel operation complete) is set, and the SCC
interrupt level is recomputed. Software that polls the counter or COC, or
enables the DMA interrupt, now sees a finished transfer.

**Debug log (DEBUG):** `DMA buffer->memory N words, memory XXXXXX, buffer XXXX`.

**Symptom if wrong:** an unexpected DMA interrupt at the level in CCR bits 0-2.

## 9. CDIC: faster XA ADPCM decoding

**File:** `opencdi/cdic.py`: `CDIC.play_audio_sector`

Nibble and byte unpacking for all 18 sound groups is done in one numpy pass.
The filter and de-emphasis loops run on plain Python ints and floats instead
of numpy scalars.

**Measured per sector (old → new):** 4-bit 1.28 → 0.87 ms, 8-bit 0.60 → 0.44 ms,
with emphasis 3.2 → 1.3 ms.
**Output:** identical samples, apart from float rounding in de-emphasis
(largest difference 0.004 on the ±32768 scale, checked over 180 sectors in
every supported coding).

## 10. MCD212: hardware cursor in 720-pixel mode

**File:** `opencdi/mcd212.py`: `MCD212.draw_cursor`

**Before:** in 720-pixel mode the picture is drawn after a 24-pixel border,
but the cursor was not shifted to match, so it sat 24 pixels left of
what it pointed at.
**Now:** the cursor is offset by the border, like the picture. 768-pixel mode
(the player menu) is unchanged.

**Debug log (DEBUG):** `cursor at X,Y drawn at x=X+24 (720-pixel mode, border 24)`
when the cursor moves in 720-pixel mode.

**Note:** this was worked out from the emulator's own coordinate handling,
not checked against MAME or hardware. If a 720-pixel title shows the
cursor 24 pixels off to the *right*, revert this item.

## 11. Serial console input

**Files:** `opencdi/__main__.py` (`start_serial_reader`), `opencdi/machine.py` (`run_frame`)

With `--serial`, lines typed on stdin now go to the 68070 UART (newline
becomes CR), so the OS-9 console can be used, not just watched. Uses
`os.read` so a blocked reader thread cannot stall shutdown.

**Debug log (DEBUG):** `serial input b'...'`.

## 12. Resource handling and clean-ups

* `Machine.close()` saves NVRAM and closes the disc image files. It is used
  when restarting with another disc and on exit (0.1.0 leaked the file handles).
  DEBUG: `closed disc image <path>`.
* A failed machine start closes the disc it opened and drops the stale
  emulator screen.
* Removed `MCD212.rom_wait_cycles` and `CSR1W_DD_BIT` (unused), and a dead
  `or name == 'eor' and False` condition in the ALU generator.
* New command-line flag `--debug`.

## 13. Test harness: `tools/run_sst.py`

* Turns trace emulation off (see item 1).
* STOP: when the CPU is stopped, the reported pc no longer adds the 4-byte
  prefetch offset. 0.1.0 reported 1,230 false STOP failures for this reason.
  Now STOP passes 2,500/2,500.

## Not changed, on purpose

* **`LINK A7`:** the 0.1.0 review said `LINK A7` stored the wrong value. That
  was wrong. SingleStepTests, recorded from real 68000 hardware, expects the
  original A7 to be stored, which is what 0.1.0 does. A change made for this
  failed all 326 `LINK A7` cases and was reverted.
* **Per-frame copy of the video planes:** measured at 0.29 ms per frame (about
  1.4% of the 20 ms PAL frame). It gives each frame a consistent view of
  video memory. Replacing it would mean redesigning the renderer for little gain.
